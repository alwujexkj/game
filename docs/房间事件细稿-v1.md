# 苏家学习乐园 · 房间事件细稿 v1

> 对应技术架构 §7 · Socket.IO 命名空间 `/room` · Redis 热状态权威  
> 目标：多设备家庭组队关（T1）可实现、可重连、可结算落库

---

## 1. 状态机

```
                    create / join
                          │
                          ▼
                      ┌───────┐
          leave/kick/ │ lobby │ ◄── again（结算后再来一局，清回合）
          expire ────►│       │
                      └───┬───┘
                          │ start（全员 ready 且房主触发）
                          ▼
                      ┌─────────┐
             超时/踢空 │ playing │ ◄── sync / 重连占位
                      └───┬─────┘
                          │ 最后一题答完 / 共享 HP 归零 / 中止通关条件
                          ▼
                      ┌──────────┐
                      │ settling │  写 Progress / stars / WeakTag
                      └────┬─────┘
                           │ 广播 settled 后关闭或 again
              ┌────────────┼────────────┐
              ▼            │            ▼
          ┌────────┐       │       （again → lobby）
          │ closed │ ◄─────┘
          └────────┘
```

| 状态 | 含义 | 允许的主要事件 |
|---|---|---|
| `lobby` | 等人、准备 | join / leave / ready / kick / start / emote / sync |
| `playing` | 对局中 | answer / emote / leave / sync；（房主可 kick 暂离位） |
| `settling` | 结算写库中 | sync（只读快照）；禁止 answer / start |
| `closed` | 已关闭 | 仅错误或引导建新房；WS 可断开 |

**转移规则（服务端强制）**

- `lobby → playing`：全员 `ready === true`（至少 2 人）、房主发 `start`，且 `levelId` 合法、同家庭。
- `playing → settling`：关卡通关条件满足，或 `shared_hp` 归零结束本局。
- `settling → closed`：Prisma 写入完成并已广播 `settled` 后自动关闭；或 TTL 到期。
- `settling → lobby`：任一成员在结算页点「再来一局」发 `again`（需仍 ≥2 人在线，否则 closed）。
- 任意 → `closed`：房间空员、过期、`expiresAt` 到达、或致命错误。

## 2. Redis 热 JSON 形状（权威）

Key：`room:{code}`（另可维护 `room:family:{familyId}` 集合索引）  
TTL：与 `expiresAt` 对齐，默认建房后 30–60 分钟；`playing` 可续期。

**`version` 约定**

- 每次服务端变更房间权威状态：`version += 1`。
- 客户端带本地 `version` 做 `sync`；若服务端更新，则推送全量 `state`（含新 `version`）。
- 客户端不得用本地乐观结果覆盖服务端；只展示，以 `answerResult` / `state` 为准。

## 3. Socket.IO 命名空间与鉴权

- **Namespace**：`/room`
- **握手 auth**（推荐）：

```ts
io("/room", {
  auth: {
    familyToken: string, // 明文 token，服务端与 Family.familyTokenHash 比对
    profileId: string
  }
})
```

- 校验失败：握手拒绝，或连接后立即 `error { code: "AUTH_FAILED" }` 并 disconnect。
- 同家庭约束：房间的 `familyId` 必须等于 token 解析出的家庭；跨家庭拒绝 `join`。
- 一人一档：同一 `profileId` 新连接顶替旧 `socketId`（重连占位），旧连接收 `error` 后断开。

## 4. 推荐接入顺序：REST 建房 → WS join

1. **房主** `POST /api/rooms` `{ profileId, levelId? }` → `{ code, expiresAt }`，并落库 `Room`（status=lobby）。
2. 房主连 `/room`，发 `join { code }`。
3. **成员** `POST /api/rooms/join { code, profileId }`（可选预检）→ 再 WS `join { code }`。
4. 大厅内 `ready` → 房主 `start { levelId }`。
5. 对局中 `answer` / `emote`；掉线重连后 `sync`。
6. 通关进入 `settling`，服务端写 Prisma，广播 `settled`，随后 `closed` 或等 `again`。

> 建房走 REST，便于码校验、限流、写 Postgres 摘要；实时态一律走 Socket + Redis。

## 5. 客户端 → 服务端事件

| 事件 | 载荷（示意） | 说明 |
|---|---|---|
| `create` | `{ levelId? }` | 可选：纯 WS 建房（不推荐主路径）；正式推荐 REST create |
| `join` | `{ code }` | 加入大厅；需已通过 namespace auth |
| `leave` | `{}` | 主动离房；若房主离开则移交或关闭 |
| `ready` | `{ ready: boolean }` | 仅 `lobby` |
| `kick` | `{ profileId }` | 仅房主；踢出目标并广播 `member` |
| `start` | `{ levelId }` | 仅房主 + 全员 ready → `playing`，生成 `seed`/`turnState` |
| `answer` | `{ questionId, answer, clientTs }` | 仅 `playing`；服务端校验对错 |
| `emote` | `{ emoteId, meta? }` | 果冻表情 / 贴纸甩出，透传广播 |
| `again` | `{}` | 结算后重回 `lobby`，清空 turn/score，保留成员 |
| `sync` | `{ version? }` | 请求全量快照；重连必发 |

---

## 6. 服务端 → 客户端事件

| 事件 | 载荷（示意） | 说明 |
|---|---|---|
| `state` | 完整 Redis 热 JSON（含 `version`） | 全量快照；join/start/sync/重大变更时推 |
| `started` | `{ levelId, seed, mode, turnState, version }` | `start` 成功后的轻量通知（亦可并入 `state`） |
| `turn` | `{ index, total, questionId, deadlineAt, version }` | 切题 |
| `answerResult` | `{ profileId, questionId, ok, turnState, score, version }` | 单次作答结果 + 权威分 |
| `settled` | `{ starsByProfile, stickers?, weakTags?, version }` | 结算完成（写库后） |
| `member` | `{ type: "join"|"leave"|"ready"|"kick"|"offline"|"online", member, version }` | 成员变动 |
| `error` | `{ code, message, detail? }` | 见 §9 |
| `emote` | `{ fromProfileId, emoteId, meta? }` | 表情广播 |

事件名前缀可选 `room:`（与架构草图一致）；实现时统一一种即可，本文默认无前缀短名，与 `room:xxx` 等价映射。

## 7. 组队模式（team modes）

| mode | 规则摘要 |
|---|---|
| `all_must_correct` | 当前题全员提交且全对才推进；有人错则本轮记错、可重试或扣星（关卡 config 定） |
| `shared_hp` | 房间共享生命值；任一人答错 `-1 HP`；HP=0 → 进入 settling（失败结算） |
| `relay` | 按 `members` 顺序接力；仅 `relayCursor` 指向者可 `answer`；答对推进 cursor/下一题 |

`mode` 来自 `Level.configJson.teamMode`（或工坊 `compiledConfig`），在 `start` 时写入 Redis。

## 9. 错误码

| code | 含义 |
|---|---|
| `AUTH_FAILED` | familyToken / profileId 无效 |
| `ROOM_NOT_FOUND` | 码不存在或已过期 |
| `ROOM_FULL` | 人数达上限（家庭三角色 → 建议 max=3） |
| `ROOM_CLOSED` | 房间已 closed |
| `WRONG_FAMILY` | 非本家庭房间 |
| `NOT_HOST` | 非房主调用 kick/start |
| `NOT_READY` | start 时仍有人未 ready |
| `BAD_STATE` | 当前状态不允许该事件（如 playing 时 ready） |
| `ALREADY_IN_ROOM` | 同 profile 已在其他未关闭房间（策略可选：顶替） |
| `LEVEL_INVALID` | levelId 非 team 轨或不存在 |
| `ANSWER_DENIED` | 非当前答题人（relay）/ 已提交 / 非 playing |
| `RATE_LIMITED` | 建房或 answer 过于频繁 |
| `INTERNAL` | 未分类服务端错误 |

`error` 载荷：`{ code, message, detail? }`；客户端用 `code` 分支，`message` 可直接给果冻气泡文案。

## 10. 结算时 Prisma 写入点

进入 `settling` 后，**同一事务（建议）**完成：

1. **`Progress`**：upsert `profileId + levelId`，`stars` 取 max(旧, 本局)，更新 `bestCombo` / `clearedAt`。
2. **`Profile`**：`starsTotal +=` 本局新增；`weekStars +=`；`bestCombo = max`。
3. **`WeakTag`**：按本局错题 `knowledgeTag` 累加 `wrongCount`。
4. **`InventoryItem` / `Sticker`**（若关卡掉贴纸）：upsert 数量。
5. **`Room`**：`status = settling → closed`，保留 `seed`；可写最终摘要 JSON（若扩展字段）。
6. **`RankSnapshot`**：不在每局必写；由周任务按 `weekKey` 聚合 `weekStars` 时 upsert。

写入成功后广播 `settled`，再将 Redis `status` 置 `closed`（或等待 `again`）。失败则 `error INTERNAL`，保持 `settling` 可重试 settle job。

## 11. 明确非目标（本细稿不做）

- 跨家庭公开匹配 / 陌生人房间  
- 同屏轮流（本地分屏）——组队仅联网房间码  
- 语音 / 视频通话通道  
- 观战、回放、录像分享  
- 房间内聊天留言板  
- 断线超过占位窗口后的战绩「云挽回」复杂对账（仅快照重连）  
- 客户端本地权威判定最终对错  
- 超过家庭档案数的观战席 / 第四人旁观（第一版不做）
